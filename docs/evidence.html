Evidence

What each gate checks, against what, how it was shown able to fail, and what it does not prove.

A gate is written before the code it judges. To show a gate can fail there is a mutant: a one-line change to the source (or to a table, a schema or the fixtures) that the gate must catch. A mutant that survives is explained or it is a gap. The oracles are programs written for the purpose, mostly in Python; they check the code against the document, not the document against anything outside it, and the page says where that matters.

Conditions

Every figure below was printed by a script of the repository, in the document that cites it. The merged tree’s run is docs/integration.md section 3: one Mac (arm64, Darwin 25.2.0), cancho a4572ea, Python 3.14.5, numpy 2.4.6, scikit-learn 1.8.0. The machine was loaded by the mutant runs (a load average up to 36) while they ran. That changes no verdict, because a correctness gate does not depend on the load; it is the reason no time is quoted from that run. All of it is one machine. A Linux x86-64 run is not done.

The red gate

python3 scripts/gate_sklearn.py --big exits 1 and prints “G-ref (pre-registered) FAILED”. docs/models-tree.md section 10.8; the rerun on the merged tree printed the same rows as docs/bench/gate_sklearn.txt, byte for byte. What it shows. The classification forests agree with scikit-learn’s to 0.001 AUC or better, and the 1,000,000-row figure of spike F is reproduced. The regression forest is 8.1% better (lower RMSE) than scikit-learn’s on R1, against a tolerance of 3%. The algorithms differ: scikit-learn looks for exact thresholds on raw values with its own random generator, this library uses quantile bins. The diagnosis, run after the failure and labelled so in the script: scikit-learn fitted on the bin indices of this library’s own edges gives 2.8737, 3.1% from this library, and without missing cells 0.6%. So most of the gap is the thresholds on a target with a product term whose extreme values an exact splitter isolates; the remaining 3.1% with missing cells is not attributed. What it does not show: that the library is wrong (it is bit-identical to an independent oracle of its own specification), or that it is right (no regression comparison with the same algorithm exists). The tolerance was not moved. The maintainer decides whether to keep the rule and leave the gate red, to compare on bin indices only, or to drop the regression comparison.

Determinism

What was verified, and where.

  • The command line: the same data and plan give the same model bytes whatever the working directory, the spelling of the path (./, //), the line ending, a byte order mark, blank lines, the caps given or the repetition; the same command gives the same output five times (D1, docs/cli.md section 6).
  • The libraries, by thread count: linear algebra at 1, 2, 3, 4, 8 and 16 threads; linear models and k-means at 1, 2, 4, 8 and 16 (65 runs); trees and forests at 1, 2, 3, 4, 5, 8 and 16, and the benchmark scripts check the same equality at 100,000 and 1,000,000 rows (by hash, without an oracle at 1,000,000).
  • Not verified: the same bytes on another machine. Everything above ran on one Mac (arm64). The design argues the arithmetic is the same on Linux x86-64 (IEEE binary64, no fused multiply-add, no platform libm), and that is unverified. ml itself has no --threads.
  • Changed at integration: the stream kinds of the splits changed from 1, 2, 3 to 4, 5, 6 (the tree and k-means streams use 1, 2 and 3), so the assignment vectors of the splits for a given seed changed. Nothing stored depended on them (docs/integration.md section 2).

The registries, and what the integration found

docs/integration.md sections 1, 2 and 4. Six stages were written apart and merged into one tree. Git reported one text conflict; reading the stages against each other found collisions that merged without a conflict marker and were wrong.

The result: 7 model kinds, 6 stream kinds and 34 refusal codes in 3 bands. tests/t_registry.cho (5 tests) and scripts/check_registry.py fail if two stages claim one number, and the new tests were shown able to fail (with the tree’s kind set back to 3, two of them fail). Files that already existed keep their bytes: every model file the CLI writes is what it was.

What this does not prove

  • Nothing here is a claim about speed. No gate measures it; the benchmarks page has the timings and their load.
  • An oracle written from the same text shows the code does what the document says, not that the document is right. The stages that compared with an outside implementation (Python float(), numpy, scikit-learn) say where they agree and where only within a tolerance.
  • The command line builds three models. The gates of k-means and the trees judge libraries; they do not show that a verb that calls them will be right, because no verb does yet. The wiring of linear and logistic has its own gates, oracle, mutants and admission script (docs/wiring.md, docs/modules.md).
  • One machine, one operating system, one compiler revision. A second-machine run (D2) is not done.
  • Not run at integration: the benchmarks, a package-mode build of models-check, and the 1,000,000-row identity and timing runs of the tree stage beyond the defaults.
  • Open items with reproducers (docs/integration.md section 7): the red gate above; models-check traps without a message on a path containing .. (a test driver, not a library; ml checks paths itself); check.sh needs ../ml-data and ../cancho-table-main.

To rerun: sh scripts/check.sh runs the gates; the mutant runs are python3 scripts/mutants_core.py, mutants_linalg.py, mutants_models.py, mutants_metrics.py, mutants_tree.py, mutants_reader.py and mutants_cli.py, each with --check to see that every edit still applies.
