# The experiments board: a read-only page for the run records of `ml runs` (issue 57, milestone M26)

**Status: this document and its gates (section 9) are written before the page.** Section 11 is filled only with what a script of this repository printed, with its conditions. Tags as in `design.md`:
**[choice]** a decision the maintainer can overturn, **[read]** read from a document or the code, **[measured]** printed by a script here, **[open]** not decided. The text of the issue (alpibrusl/cancho-ml#57) is the scope;
the record schema, the run id and the verbs are those of `docs/tracking.md` sections 5.2 to 5.4 and are not repeated here.

`fit --track DIR` writes one record per run and `ml runs list|show|compare|verify` read them. A terminal does not scale past a handful of runs. `docs/board.html` is a page that reads the same records: a table, a comparison, a chart, and a
list of everything that is wrong with the input. It follows the pattern of cancho-code's board (one file, no server, no request, a drop target and a file picker, the DOM built from text nodes only) and keeps none of its words.

## 1. Decisions in one table

| # | question | decision | why |
|---|---|---|---|
| B1 | what the page is | one HTML file, `docs/board.html`, with one logic `<script>`, a plain-text data block for the sample, and the shared `assets/site.css` for the tokens, the header and the footer | the issue asks for one self-contained page with the landing page's tokens; "self-contained" means no request to any other host, no library and no build step |
| B2 | what is sent anywhere | nothing: no `fetch`, no `XMLHttpRequest`, no `WebSocket`, no beacon, no dynamic `import`, no `eval` | a record names a training file and column names; the page reads them on the machine they are on (section 9, G10) |
| B3 | how the DOM is written | with `textContent` and `setAttribute` only; never `innerHTML`, `insertAdjacentHTML` or `document.write` | a record is data from a file the user did not write; a column name must not become markup (G10) |
| B4 | where the logic lives | between `/* LOGIC begin` and `/* LOGIC end */` in the one script: pure functions that touch no `document`, `window` or `navigator`; the DOM code follows the marker and calls them | `node` runs the first part headlessly (`scripts/board_node.js`), so the gates test the code the page runs |
| B5 | the `ml` binary | unchanged | this stage is a page and its checks; section 10 says what a later `--format` of `list` could add |
| B6 | the primary metric | by the record's `task`: classification `accuracy`, regression `rmse`, clustering `inertia`; a record without that member (a constant model has `metrics: null`) shows no value | the metric each task's `eval` prints first for the question "how good is it"; the column says which one it shows (section 5) |
| B7 | the id recomputation | SHA-256 of the exact bytes of the `inputs` object as they stand in the text read (`docs/tracking.md` 5.2); if that differs and the compact re-serialisation of the parsed object matches, the record was reformatted: a note, not an error | the id is defined over bytes, so the page hashes bytes; a pretty-printed copy of an honest record must not be called forged |
| B8 | the `check` recomputation | SHA-256 of every byte of the record before `,"check":"` (5.3), when the record is in canonical form | the same rule the tool applies |
| B9 | what the page cannot do | it cannot `verify`: a replay needs the training file and the compiler build, so the page shows `ml runs verify DIR ID` to copy and says that only the tool can run it | the page's integrity check shows that a record is consistent with itself, not that its model is reproducible; the page never says "verified" |
| B10 | the sample | a plain-text block of real records (section 7), generated by `scripts/site.py` from the built binary, loaded by a button; its caption says it is a sample of real records | a visitor with no records of their own can see the page work |

## 2. What is read

The user gives text: files from a picker (several at once), files dropped on the page, or text pasted into a box or onto the page. Each text is split into JSON documents by a scanner that knows strings and escapes (`splitDocs`):
the documents are the top-level objects and arrays; text between them (a shell prompt line, a log line) is **junk** and is reported, not dropped silently. A text that ends inside an object is `not-json` (the text was cut).

Each document is classified, in this order:

| the document | read as |
|---|---|
| `{"ok":false,...}` | a refusal of the tool: problem `refusal`, naming the `rule` |
| an `ml.v1` answer with `data.runs` (or a bare `{"dir":..,"runs":[..]}`) | the answer of `ml runs list`: one **list row** per run (`id`, `model`, `task`, `data_sha256`, `model_sha256`, `train_rows`, `metrics_on`, `evals`) |
| an `ml.v1` answer with `data.record` (or a bare `{"record":{..}}`) | the answer of `ml runs show`: its record, read as the record below with the bytes of the nested object |
| an `ml.v1` answer with `data.a`, `data.b` and `data.inputs` | the answer of `ml runs compare`: problem `compare-answer` (the page compares by itself) |
| `"schema":"ml.run.v1"` | a **run record** |
| `"schema":"ml.eval.v1"` | an **eval record**, attached to the run named by its `run` member |
| `"schema"` starting `ml.run` or `ml.eval` with another version, or an answer of another `schema` | problem `schema-version`, naming the version found and the one read; not shown as a run |
| any other JSON value | problem `not-a-record` |

A text with no JSON document in it (a CSV, a model file, a number) is `not-json`; a text with nothing in it is `empty`; text around documents is one `junk` note per source (the first piece is quoted). Every problem names its source (a file name, or `pasted text`, or `sample`).

## 3. The integrity check

For each run record the page computes, in the browser, with `crypto.subtle.digest("SHA-256")` when it exists and with a pure JavaScript SHA-256 when it does not (`file://` pages and plain-HTTP origins may lack `subtle`: the fallback is
used and tested, and the two are equal on every vector of G1):

* `id`: the SHA-256 of the raw `inputs` object. Equal to the record's `id` member: fine. Different: **`id-mismatch`** (error), with the first 12 digits of what it computed. If the compact form of the parsed `inputs` hashes to the id,
  the file was reformatted: `reformatted` (note), and the `check` cannot be checked (it covers bytes the page no longer has).
* `check`: the SHA-256 of the record's bytes before `,"check":"`. Different: **`check-mismatch`** (error). A record whose `inputs` byte was changed has both; a record whose metric was changed has the second only (the id covers the inputs, not the metrics).
* the file name: a file named `<64 hex>.json` whose digits are not the record's `id`: **`name-mismatch`** (error; a record copied under another run's name).
* the shape: the members of 5.3 with their types, `id`, `check` and the three hashes as 64 lowercase hex digits, `task` one of the three, `metrics` null or an object with `rows`, `on` and `metrics`, no repeated top-level `id`, `inputs` or `check`: else
  **`malformed`** (error) naming the member. A malformed record is still a row (with what could be read), marked.
* duplicates: two records with one `id`: **`duplicate-id`**, an error when their bytes differ and a note when they are the same record read twice; the first stays in the table, the second is listed in the problems and not shown. Two eval records with one `check`: a note.
* the list against the records: when a list row and a record carry one id and disagree on `model`, `task`, `data_sha256`, `model_sha256`, `train_rows` or `metrics_on`: **`list-disagrees`** (error). A list row with no record is shown as `list only`: its id cannot be recomputed
  (the list holds no `inputs`), and the page says so once per list (`list-only`, note).
* an eval record whose run is not loaded: `eval-orphan` (note); eval records loaded for a run whose number differs from the `evals` of its list row: `evals-count` (note).

The problems list is a visible section of the page, always shown, with its count in the heading; with none it says that no problem was found in N inputs. A problem is never reduced to a colour: it carries the word `error` or `note`.

## 4. The table

One row per run (record rows, then list-only rows), in the columns of the issue: **id** (12 of 64 digits; the full id in a `title` and in the detail), **model** (from the plan's last line `model kind=K`, the word the list prints), **task**, **train rows** (`counts.train_rows`),
**split** (the record's split text), **metrics on** (`held-out`, `train`, or none), **primary metric** (section 5), **data** (12 digits of the training file's SHA-256), **evals** (the eval records loaded for the run, or the list's count when a list
row is present), **record** (the integrity verdict in words: `ok`, `id mismatch`, `check mismatch`, `reformatted`, `list only`, `malformed`) and a **copy** button for `ml runs verify DIR ID`.

* **Sort** by every column: a button in the column header, `aria-sort` on the header, ascending first. The rule is fixed and tested: numeric columns by value, text columns bytewise (`<` on the strings, not locale order), a missing value last in both
  directions, ties broken by `id` ascending. The default is `id` ascending, which is the order of `ml runs list` (sorted by id, bytewise).
* **Filter** by model, by data hash (the runs on the same data: each choice shows its count), and by an input: a list of the inputs that take more than one value across the runs shown (`plan`, `seed`, `split`, `data.sha256`, ...,
  the dotted keys of `ml runs compare`); choosing one adds a column with its value and a second list to keep the runs with one value.
* **Select** up to two runs (checkboxes). A third replaces the older selection.
* **Detail**: the id button of a row opens the run below the table: the full id, the commands to copy, the inputs, the counts, the metrics and the verdict of the integrity check.

## 5. The primary metric **[choice]**

`classification` shows `accuracy`, `regression` `rmse`, `clustering` `inertia`: the first member of the object `eval` prints for each task that the task's reader looks at, and the one the demo's landing log quotes. The cell shows the number rounded to six significant
digits and the exact text in its `title`; the metric's name and the `on` marker are shown beside the number, because an `accuracy` on training rows and one on held-out rows are not comparable, and the chart marks them differently. A record whose
`metrics` is null (a constant model) or lacks the member shows an empty cell and sorts last. The metric values of a record are the texts the tool prints (`"0.9333333333333333"`); the page keeps the text and computes with `Number(text)` only to order, to
subtract and to draw.

## 6. Compare and the chart

**Compare** is `ml runs compare` (5.4), recomputed from the two records, with the same answer field for field (`a`, `b`, `inputs`, `metrics`, `model_equal`) and one member added, `delta` in each metric entry (`b - a`, null when either side is not a number). The rules, read from
the tool and tested against it on every ordered pair of the gate's runs: `inputs` lists the members of the two `inputs` objects that differ, in the order of the first record, then those only the second has; two members that are both objects are compared member by member with a dotted key
(`data.sha256`, `reader.max_categories`), otherwise as a whole (`reader` null against an object is one entry); `metrics` lists the metric names of the first record in order, then those only the second has, a member missing on one side is null there, `equal` is deep
equality of the two values (they can be lists: `sizes`, `mean_distance`); `model_equal` compares the two model SHA-256 digests. The page shows the differing inputs, the metrics side by side with the difference, whether the model files are the same, and the `ml runs compare DIR A B` command to copy.

**The chart** draws one metric across the runs shown, in table order: one horizontal bar per run, labelled with the run's 12 digits and model, with the value written at the end of the bar; the axis starts at zero (or at the smallest negative value). Bars of runs scored on training rows are
hatched and say `train` in their label. The metric list holds the scalar metrics found in the records; the default is the primary metric most runs share. A run without the metric is named under the chart as left out. The chart is an inline `<svg role="img">` with a title and a description, and the same values are
a table in a `<details>` beside it (no information is only in the picture).

## 7. The sample

`scripts/site.py` writes the block `gen:sample` of `board.html`: the records of the runs below, one per line, exactly as the tool wrote them, from the built binary in a temporary directory on `docs/examples/data/iris_train.csv`:

1. the first fit of `scripts/demo.sh` (the same command, `--l2 0.1`), run `d659c3217b4c...`;
2. its second fit (`--l2 1.0`), run `519af537b8b7...` (the two ids of the landing page's replay);
3. a k-means fit on the same file with `--drop virginica` (so that a second task and its primary metric, `inertia`, show);
4. the eval record that `ml eval --track` writes for run 1 on `iris_test.csv`.

The ids and the hashes are the same on every run (the records hold no time and no host name). The caption says the sample is real records, which two of them the demo prints, and that they are the files `fit --track` and `eval --track` wrote. `site.py --check` fails when the block differs
from what the binary writes; `check_board.py` checks that the page's own logic finds no problem in it and that its ids equal those of a fresh run (G9).

## 8. Layout, themes, keyboard **[choice]**

The landing page's tokens only: no colour token is added, and the inline stylesheet of the page holds no colour literal (G10), so every pair it uses is a pair `scripts/check_contrast.py` already measures. Light and dark follow `prefers-color-scheme`. At 360 px the page has no horizontal scroll: the controls wrap,
and the table scrolls inside its own focusable, labelled region. The header is the generated one (`gen:nav`) with the link `Board` (hidden below 40rem like the other optional links, as the landing page's "How it works"); the footer is `gen:foot`. One `<h1>`, `lang`, a skip link to `<main id="main">`. Every control is a native
`button`, `input`, `select`, `summary` or link with a visible label and the focus ring of `site.css`; nothing is a `div` with a click handler. Changes that the user cannot see (a load, a clear) are announced in a `role="status"` line. No `localStorage`, no cookie: nothing is remembered.

## 9. The gates (written first; each can fail)

`scripts/check_board.py` makes the runs itself with the built binary (`scripts/demo.sh` cleans up, so it does not reuse its directory; it runs the demo's two fits and a larger set in its own temporary directory), writes the records, the answers of `ml runs list`, `show` and `compare` for every run and every
ordered pair, and runs the page's logic with `node scripts/board_node.js` on them.

| gate | what must hold |
|---|---|
| G1 | the SHA-256 of the logic (pure JavaScript) equals `hashlib` on the vectors: empty, `abc`, lengths 55, 56, 57, 63, 64, 65 and 119, 120, 128, one MiB of seeded bytes, a text with multibyte characters; `makeDigest` picks `crypto.subtle` when present and the pure function when `crypto` is removed, and both give the same digest |
| G2 | for every run, the id the page recomputes from the file's bytes equals the id the tool wrote and `check` verifies; the same rows come from the three forms of input (the `DIR/*.json` files, `ml runs list` plus the records, the `ml runs show` answers, and one pasted text holding all of them); the fields of each row equal the `ml runs list` answer's |
| G3 | a record with one `inputs` byte changed is `id-mismatch` and `check-mismatch`; one metric byte changed is `check-mismatch` only; a changed `id` member is `id-mismatch` and `check-mismatch` (the check covers the id member); a changed `check` is `check-mismatch` only; a pretty-printed copy is `reformatted` and no error; a record under another id's file name is `name-mismatch` |
| G4 | a duplicate id (the same record twice, then two that differ), an `ml.run.v2` record, an `ml.eval.v2` record, a non-record JSON (an array, an object without `schema`, a refusal, an `ml runs compare` answer), a file that is not JSON, an empty file, a cut file, a prompt line around a record, a list row that disagrees with its record, and a list-only run each give the problem of section 3 with its code and its source, and the rows that should be shown are shown |
| G5 | the page's `compare` equals the tool's answer field for field on every ordered pair of the runs (including a run against itself, a constant model against a linear one, two k-means runs, runs whose `reader` differs, and a classification against a regression), and its `delta` equals `b - a` computed by Python |
| G6 | the table: every column sorted ascending and descending equals an order computed independently by this script from the documented rule (numeric, bytewise, missing last, ties by id), the default order equals the `ml runs list` order, and each filter returns the rows an independent filter returns |
| G7 | the primary metric: classification `accuracy`, regression `rmse`, clustering `inertia`, none for a constant model, the value equal to the record's text |
| G8 | the chart data: the bars (order, ids, values), the axis range, the runs left out and the default metric equal an independent computation; the bar widths are proportional to the values |
| G9 | the sample block parses with no problem, holds three runs and one eval, and its records equal, byte for byte, the records of a fresh run of the same commands |
| G10 | the structure of the file: the size budget (section 12), one `<h1>`, `lang`, the skip link, a viewport, the title and description in the SEO limits, no `src` or `href` that leaves the site (only `assets/site.css`, the icon and the pages), none of `fetch`, `XMLHttpRequest`, `WebSocket`, `sendBeacon`, `import(`, `eval(`, `new Function`, `innerHTML`, `insertAdjacentHTML`, `document.write`, `localStorage`, `sessionStorage` in the script, no `document`, `window` or `navigator` in the logic part, no colour literal in the inline stylesheet, the dark scheme and the 360 px rule present, every `input`, `select` and `textarea` labelled, no click handler on a non-interactive element, the statements of sections 3 and 1 (B2, B9) in the page's text, and the sample's caption |

`scripts/mutants_board.py` applies each of these faults to a copy of the page and runs `check_board.py` on it with the fixtures of the control run; each must be killed or explained: the sort direction, ties, missing-last, the id recomputation (hashing the whole record, the compact form
only), the `check` prefix, the compare diff (no dotted keys, `equal` always true, `model_equal`, the order of `metrics`, the sign of `delta`), the primary metric of each task, each integrity flag (the id, the check, the schema version, the duplicate, the non-record, the name), the filters, the chart's range and
order, the SHA-256 constants, the sample, and the structure rules (a `fetch`, an `innerHTML`, an external script, a colour literal, the size).
The landing page's card is covered by `scripts/check_landing.py` and `scripts/mutants_site.py` (section 9 of the landing tests: the card of the board, the header link on the six pages).
The checks that need a browser (the DOM code, 360 px without a horizontal scroll, light and dark, focus) are made in the built-in browser and reported in section 11; they are not scripted here.

## 10. What a future `--format` of `list` could add **[open]**

`ml runs list` has no metric today: its row is `id`, `model`, `task`, `data_sha256`, `model_sha256`, `train_rows`, `metrics_on`, `evals`. The page reads the metric from the records, so it needs no change in `ml`. A `--format` of `list` that prints each row with the primary
metric (its name and text), the split text and the schema version of the record would let a list alone fill the table's metric and split columns, and would give the page the schema version without the records. It would need the rule of section 5 in the tool, a golden, and
the rule tags and schemas that every verb carries; it is not done. A generated `ml runs board DIR > board.html` (deterministic, the records embedded) would cost the size of the page in the binary for what `cat board.html records.txt` gives; it is not done.

## 12. Size budget **[choice]**

`docs/board.html` at most 48 KB (49,152 bytes), its logic script at most 32 KB, `board.html` with `assets/site.css` at most 72 KB. The page loads no image. Section 11 gives the measured sizes; the budget is a gate (G10), not a measurement.
