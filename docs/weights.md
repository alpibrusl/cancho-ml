# cancho-ml sample weights (issue 59 item 1, stage C of `multiclass.md`)

**Status: a specification, written BEFORE any code of this stage. Every number that a script of this repository has not printed is marked [choice], [open] or [read]; section 7 is filled in after the gates have run.** Tags as in `design.md`: **[choice]** a decision the maintainer can overturn, **[read]** read from a document or the code, **[open]** not decided or not yet checked. A claim found false is corrected in place and marked.

Nothing weights a row today: no flag of the tool takes a weight, and the tree, forest and boost lists name sample weights as not built (**[read]** `models-tree.md` section 1, `models-boost.md` section 1). Weights are needed for imbalanced data and for importance weights, and they are the first piece of the logged-bandit line of issue 59 (off-policy evaluation and policy learning need the inverse of a propensity as a weight).

## 1. The flag and its meaning

`--weight COL` on `fit` and `cv`: the column that holds the weight of each row. **[choice]** `eval` takes it in a later stage (the weighted metrics are a section of their own: their exact-integer forms become float sums); `predict` and `ml-serve` take no weight, so asking for one is the refusal of an unknown flag as today.

* The weight column is a numeric column of the file; it is **not a feature** (the model's schema does not list it) and it is not the target (`args.conflict`, exit 2, when `--weight` names `--target`). It is read as a float, and a column named by `--drop` or `--cat` is not usable as the weight (`args.conflict`).
* A weight is finite and `0 <= w <= W_max`, `W_max` = 1e12 **[choice]**: a bound under which the sums of up to `2^20` rows stay far from overflow and from the point where adding a small weight to a large sum loses all of its digits for the sizes the tool takes (**[open]** the second claim is checked by gate WG6, not assumed). A negative weight is `ml.weight.negative`, a non-finite one `ml.input.non-finite` as any cell, a missing cell `ml.weight.missing`, one above `W_max` `ml.weight.too-large` (all exit 8, the line and column in `detail`). The sum of all weights being 0 is `ml.weight.zero-total` (exit 8).
* **The meaning of a weight `w` is `w` copies of the row** in every loss, gradient, hessian, impurity and mean the fit computes. Counts that are limits or guards still count rows, not weights **[choice]**: `min-leaf`, the row ceilings, the validation split of early stopping and the stratified splits of `cv` are about rows. A row of weight 0 is a row that contributes nothing to any sum; the bins of the trees are computed from all the rows given to the fit, as today (**[read]** `models-boost.md` 2.1), so removing a zero-weight row from the file changes the bin edges of a tree and the equivalence of gate WG3 does not claim it for the models that bin.
* The weights are not normalised, and the regularisation keeps the form each model has (**[read]** `models-linear.md`): the ridge objective is the **sum** of squares plus `l2 ||w||^2`, so weights `c w` with `c l2` give the model of weights `w` with `l2`; the logistic objective is the **mean** negative log-likelihood plus `l2 / 2 ||w||^2` (the form that makes the oracle's scikit-learn `C = 1 / (l2 n)` correspond, `models-linear.md`), and with weights the mean is taken over the **sum of the weights**, so that a weight `w` is `w` copies of the row and the weights `c w` with the same `l2` give the same model. These are gate WG4, stated for those two models only.

## 2. Model by model

| model | what the weight multiplies | arithmetic |
|---|---|---|
| `linear` | each row's term in the normal equations, `X' W X` and `X' W y` | the decisive sums of `linalg.order`, now with the weight in each term, in the same block order, so the result is the same at any thread count **[open]** the weighted Gram matrix goes through the same Cholesky and the same relative pivot test; the test is a ratio, so it is unchanged in kind |
| `logistic` | each row's gradient and hessian term, and its term of the summed loss | the same sums; the separation test compares the **weighted** summed loss with its bound, which assumes weights of at least 1 to be meaningful for a count and is otherwise a different quantity: **[open]** gate WG7 decides whether the test is applied to the weighted loss divided by the sum of weights, and the answer is written in section 7 |
| `tree`, `forest` regression | the node sums `Sm`, `s_b` and the node size used in the gain | the sequential float sums in the node's row order of `models-tree.md` 3.2, with `w_i y_i` and `w_i` accumulated |
| `tree`, `forest` classification | the class counts of a node | **a new path**: the exact integer Gini of `models-tree.md` 3.1 needs integer counts and cannot take a float weight. A weighted classification tree computes the Gini decrease in floats from the weighted class sums, in the node's row order **[choice]**. The unweighted path and its exact comparison are unchanged and are the only path used when no `--weight` is given |
| `forest` | the bootstrap draw stays a draw of rows (uniform, stream kind of the forest); the weight enters each tree's sums | |
| `boost` | the gradient and the hessian of each row, so the Newton leaf `-G / (H + lambda)` and the split gain | the gradient and hessian are multiplied by `w_i` before they enter a histogram; the row subsample draws rows, not weights |
| `kmeans` | **not supported**: `--weight` with `--model kmeans` is `args.conflict` with the repair "drop --weight: k-means here has no weighted centroid" **[choice]** | |
| `constant` | the weighted mean or the weighted majority | **[open]** the exact-integer form of the constant model's file (`mfile.cho`: counts as i64) cannot hold a float weighted mean; `--weight` with `--model constant` is `args.conflict` until a weighted form is chosen |

### 2.1 The order of the work [choice]

The stage is cut in four pull requests, each with its gates: **C1a** the library functions of the linear and the logistic regression (this section 2.2 and 2.3); **C1b** the flag, the column, the refusals, `fit`, `cv`, `describe`, the provenance and the servers for those two models, every other model answering `args.conflict` for `--weight` until its own piece lands; **C2** the regression and classification trees and the forest (the float path of section 2); **C3** boosting. The softmax regression (`spass`) takes the same per-row multiplication as the logistic one and is a smaller piece after C1b. Nothing of C1a is reachable from `ml`.

### 2.2 Linear regression: the rows scaled by the square root of the weight [choice]

`fit_weighted(x, y, w)` forms `s_i = sqrt(w_i)` (the IEEE square root, correctly rounded on every platform), the matrix `Xs` with `Xs[i][j] = s_i * x[i][j]` (one rounding), `ys_i = s_i * y_i`, and runs the **unchanged** sums on `Xs`, `ys` and the vector `s` in the place of the column of ones: `G = Xs' Xs` (the package's `syrk`), the column sums `Xs' s`, `Xs' ys`, `sum(ys * s)`, and the corner `sum(s * s)` by the package's `dot`, all in the order of `docs/linalg.md` section 2, so the result is the same at any thread count by the same argument as the unweighted fit. The ridge, the Cholesky and the pivot test are unchanged. For `w_i = 1` every `s_i` is exactly 1, `Xs` is `X` bit for bit and the corner is `n` (an integer below 2^53 is exact in any order): the weighted function with unit weights returns the bytes of `fit` (gate WG2). A weight is therefore seen as `s_i * s_i`, which differs from `w_i` by about one unit in the last place; "w copies of the row" holds to that, not exactly (gate WG3 uses a bound). The cost is one copy of the matrix (`n * d * 8` bytes) and of `y`, which is part of the budget the caller checks.

### 2.3 Logistic regression: the three row terms times the weight [choice]

The Newton pass of `npass.block` computes, per row, `r = p - y`, `s = p (1 - p)` and the loss term. The weighted pass multiplies the three by `w_i` right after they are formed (each product rounded once), and then goes on as before: the gradient receives `fl(r w) * a_ia`, the Hessian `fl(fl(s w) * a_ia) * a_ib`, the bias row `fl(s w)`, the loss `fl(loss w)`. With `w_i = 1` the products are exact and the pass is the unweighted one bit for bit; with no weights the code is not run (the weights slice is empty). The divisor `n` of the mean is replaced by `Sw`, the sum of the weights by the package's `dot` of the weights with ones (the same order at any thread count), computed once before the iterations; the objective, the gradient and the Hessian keep their form with `Sw` in place of `n`, and `l2` is added as before, so weights `c w` with the same `l2` give the same model (up to rounding).

The **separation tests** read the weighted quantities. The loss test of `refusals-fit.md` D2 compares the summed loss with 0.6931 because that bound makes every row's own loss smaller than ln 2; with weights the sum is `sum w_i loss_i`, and it is below `wmin * 0.6931`, `wmin` the smallest positive weight, only if every row with a positive weight has `loss_i < 0.6931` (each term is nonnegative and `w_i >= wmin`), so the test is `weighted loss < wmin * 0.6931`; for unit weights `wmin = 1` and it is the unweighted test. A row of weight 0 is not part of the test. The scale test is the weighted root mean square of the predictor, `sqrt(w' G w / Sw)` with the Gram matrix of the weighted pass 0, against the same bound 50.

### 2.4 The wiring of C1b: the flag, the column and the refusals [choice]

* **The flag.** `--weight COL` on `fit` and `cv` (the two verbs of the table that fit), `COL` a header name compared byte for byte. `--model linear` and `--model logistic` take it, whether named by `--model` or by the model line of a `--plan`; every other model (constant, k-means, tree, forest, boost, softmax) answers `args.conflict` (flags `--weight, --model`; the repair says that model has no weighted fit yet and names this document). `predict`, `eval`, `importance`, `dump`, `describe` and the servers do not list the flag: they answer `args.conflict` as for any flag a verb does not take. The held-out part of `fit --split` and the test folds of `cv` are scored **unweighted** (the weighted metrics are a later stage, section 6).
* **The column.** The weight column stays in the matrix the reader makes, like the target, and is **not a feature**: it is left out of the schema stored in the file (so `predict` neither needs nor accepts it), out of the columns handed to the plan and out of the feature count. `--weight` naming the target, a column of `--drop` or a column of `--cat` is `args.conflict`; a name that is not in the header is `ml.input.unknown-column` with the flag `--weight`. The cells go through the reader as any numeric column: a cell that is not a number is `ml.input.non-numeric` and one that is `nan`, `inf` or out of range is `ml.input.non-finite` (the rules and details of the reader, the repair that proposes `--drop` withheld for this column). The values then go through the checks of section 1, each with the row (1-based, after the header) and the column name in `detail`: `ml.weight.missing` (an empty cell), `ml.weight.negative`, `ml.weight.too-large` (above `1e12`) and `ml.weight.zero-total` (no row of the training side has a weight above 0; `detail` has the side). The four are new rule tags, exit 8, no repair.
* **The fit.** The weights of the training rows (the same rows as the labels: all of them, the training side of `--split`, or the training folds of `cv`) go to `fit_weighted` of section 2.2 or 2.3. The steps of the plan (impute, scale, bucket, encode, freq, hash) are fitted **unweighted** on the same rows **[choice]**: a step is a function of the feature values, and a weighted step would be a stage of its own. A fit refused by the library (collinear, separable) answers the same refusals with the same details; with weights the separable record is the weighted one of section 2.3.
* **What is recorded.** The file keeps its bytes: it does not record the weights (nothing of them is needed to predict), so `describe` does not show them **[choice, replaces the open question of section 3]**. The answer of `fit` and of `cv` names the weight column (`"weight": "COL"`, absent without the flag), and the run record of `--track` keeps the column in its inputs, so that `ml runs verify` replays the fit with the flag (gate WG8). The JSON lines input takes the flag with the same column rule.

### 2.5 Trees and forests: the weighted growth of C2 [choice]

C2 is cut in two pull requests: **C2a** the library (`tree.grow`, `tree.forest`, the adapters, the driver and the oracle) and **C2b** the wiring (the dispatch, `train`, the command-line tests and the wire oracle). Nothing is reachable from `ml` before C2b.

The unweighted growth (`models-tree.md` section 2) is **not touched**: `grow` takes a vector of weights `wt` that is empty without `--weight` and every unweighted line of it runs as before (gate WG1: the tree oracle, the planned baseline and the fingerprint golden are unchanged). With weights, the same function takes the weighted branches below. The bins (`models-tree.md` 2.3) are computed from the rows given to the fit as today, weights ignored, so a zero-weight row still shapes the bin edges (section 1).

* **Bootstrap.** A forest draws rows uniformly with replacement, as today (`models-tree.md` 2.2); a row drawn `c` times is `c` occurrences, each with the row's weight. The weights do not change the draw.
* **Counts still count rows.** `min-leaf`, the row ceilings and the `na` and `nb` count records of the payload are row counts of the bootstrap sample, as now. The payload keeps its shape and its bytes' meaning; nothing of the weights is needed to predict.
* **The node sums.** For a node of rows `idx[lo..hi)` (in the node's row order, a function of the bootstrap order alone), every weighted sum is a **sequential float sum in that row order**, as the regression sums are today (`models-tree.md` 3.2):
  * classification: `W0`, `W1`, the sum of `w` over the occurrences of class 0 and class 1, `W = W0 + W1`;
  * regression: `S = sum(w * y)` (the product rounded once, then added), `W = sum(w)`.
* **Histograms.** Per bin: the row count (an int, as now) and the float sums above, each a sequential sum in row order of the rows in that bin. The weighted path scans **one feature at a time** (the four-wide histograms of the unweighted path are a speed device for ints): features are still taken in ascending order of the node's subset, so the result does not depend on the grouping; no speed is claimed.
* **Candidates.** The left side of bin `b` (and of the missing variant) has the running sum of the bin sums in ascending bin order (`WL0 = h0 + h1 + ...`, a sequential sum of the bin sums); the right side is the node total minus the left (`WR0 = W0 - WL0`), as the regression `sr = sm - sl` is today. A candidate needs, as now, `nl >= min-leaf` and `nr >= min-leaf` (rows), **and `WL > 0` and `WR > 0`** (a side with no weight has no value to predict). The score replaces the best only if strictly greater, the first candidate winning a tie, in the order of today (feature ascending, bin ascending, variant 0 then 1, the variant 1 skipped when no row is missing):
  * classification: `score = (WL0 * WL0 + WL1 * WL1) / WL + (WR0 * WR0 + WR1 * WR1) / WR` with `WL = WL0 + WL1`, `WR = WR0 + WR1`, each operation rounded in the order written (the Gini decrease, up to a constant of the node, as the exact integer form is today);
  * regression: `score = SL * SL / WL + SR * SR / WR`, `SR = S - SL`, `WR = W - WL`.
  This is a float comparison where the unweighted classification is an exact integer one: a **float tie or a one-ulp difference can order two candidates differently from the exact rule**, so unit weights are not claimed to give the unweighted classification tree as bytes (gate WG2 measures how often they do).
* **When a node is a leaf.** The depth and `2 * min-leaf` tests are those of today. A classification node is pure when `W0 == 0` or `W1 == 0`; a regression node when its rows with a weight above 0 all have one target. **Rows of weight 0 take no part in purity**: a node of one class apart from rows of weight 0 is a leaf.
* **Leaf values.** Classification: `W1 / (W0 + W1)`; regression: `S / W`. A node whose total weight is 0 can only be the root of a bootstrap sample that drew rows of weight 0 only (every child has a side with weight, by the candidate rule): its value is the **weighted value of the whole training set** (`sum(w y) / sum(w)`, a sequential sum in row order, computed once and passed to `grow`).
* **Forest.** Trees are grown one per stream as today; the aggregation over the trees (`models-tree.md` 2.6) is unchanged.
* **The library functions.** `forest.fit_weighted` takes the weights beside the labels; the weights go through `check_weights` of `models.common` (finite, 0 to 1e12, not all 0) and the class check is made on the rows with a weight (both classes need a row of positive weight), as for the logistic regression.

## 3. The file

A model fitted with weights is the same kind with the same payload shape: nothing of the weights is needed to predict. **[choice]** The provenance section (**[read]** `docs/tracking.md` section 2) records that a weight column was used and its name, so `describe` can say so and `ml runs verify` replays the fit with the same flag (the run record keeps the command line; **[open]** whether the record needs a field of its own or the flag in the command is enough is checked by gate WG8). Whether this is a new member of the provenance section, and so a change of the optional section's bytes only for a weighted fit, is decided at the review of this document; a file with no weights keeps its bytes.

## 4. Where the work is

`tools/ml` (the flag in `spec`, the reading of the column in `wireio` and `csvload`, `wire` and `verbs` to hand the weights to the fits), `lib/models/linear`, `lib/models/tree`, `lib/models/boost` (the sums), `lib/core` for the refusal codes, `mdesc` and the schemas for the `describe` member. The generated tables change where a flag or a tag appears.

## 5. Gates (written first; each can fail)

| gate | what | must be able to fail by |
|---|---|---|
| WG1 | **binary bytes unchanged**: with no `--weight`, every file and answer is equal to the one before the stage, by the fingerprint golden of `docs/bench/xplat_fp.txt` on every platform | a weighted code path taken without the flag |
| WG2 | **all weights 1.0 equal no weights**, as bytes, for the models whose sums are floats in a fixed order (linear, logistic, regression tree and forest, boost) **[open]**: this should hold because `w * x` with `w = 1.0` is `x` exactly; where it does not (a sum that is reassociated for the weights), the difference is explained in section 7 and the gate is a bound | a multiplication that is applied to one sum and not another |
| WG3 | **duplication**: integer weights `w_i` give the model of the file in which row `i` appears `w_i` times, for the linear and logistic regression within a bound fixed in advance on the coefficients (the sums are in a different order, so bytes are not claimed), and for the trees and boost as a property of their splits on data without ties in the bins | a weight applied once too often |
| WG4 | **scale**: weights `c w` with `c l2` equal weights `w` with `l2` for the linear regression, and weights `c w` with the same `l2` equal weights `w` for the logistic regression, within a bound fixed in advance (a power-of-two `c` is exact in the products and is the first control) | a penalty that is not scaled, a mean taken over the rows instead of the weights |

| WG7 | **separation** with weights: a fixture of separable classes with `l2 = 0` is refused and one with a few rows of weight `0` is judged on the rows that have weight | a test that reads the unweighted loss |
| WG8 | **replay and provenance**: `ml runs verify` of a weighted fit gives the same bytes | a record that loses the flag |
| WG9 | **thread invariance** (1, 2, 4, 8) of every weighted fit; **fuzz** of hostile weights (zero rows, all zero, negative, `nan`, `inf`, `1e308`, an empty cell, the target or a dropped column named as the weight) and of damaged files; **mutants** of the new code, all killed or each survivor explained; **admission**; no source file over 2,000 lines | — |

## 7. Results

### 7.1 Stage C1a: the linear and the logistic regression, library only

Machine: Linux x86-64, 4 cores, one run of each script, nothing else deliberately running; the compiler at `0207556`. Nothing here is a speed figure.

* **WG5, the oracle (bytes).** `scripts/oracle_models.py --suite` has 22 weighted cases (11 linear, 11 logistic, kinds 1 to 4 of weights, `n` from 30 to 20,000, ridge and no ridge, a zero weight at every fifth row in kind 4), and `--thread-suite` 4 more at 1, 2, 4, 8 and 16 threads: every parameter, every raw decisive sum of every iteration and the hash of the predictions equal the oracle's bit for bit ("suite: all bits equal"). The oracle is the numpy port of section 2.2 and 2.3 and calls no BLAS.
* **WG2, unit weights.** The two unit-weight cases (kind 1) are compared with the driver's own unweighted fit as bytes, and `tests/p_weights.cho` does the same at 1 and 4 threads with the library: equal (**the claim of section 2.2 and 2.3 holds**: `sqrt(1.0) = 1.0` and `x * 1.0 = x`).
* **WG3, WG4, WG6, WG7, WG9, `tests/p_weights.cho`** (8 tests, all ok; bounds fixed in the file before the numbers were seen): integer weights against the file with the rows repeated, and zero weights against the file without those rows, within 1e-8 relative, linear and logistic; weights `1024 w` with `1024 l2` (linear) and the same `l2` (logistic) within 1e-12, `1e6 w` within 1e-9; every weight at `1e12` and every weight at `1e-300` within 1e-9 of the unweighted fit, with finite parameters; the refusals of section 1 (negative, above 1e12, NaN, infinity, all zero, a short vector; exactly 1e12 is accepted; all rows of one class at weight 0 is `ml.label.single-class`); separable classes refused with `l2 = 0` and fitted with a ridge, the same classes with one relabelled row refused only if that row has a weight, and **overlapping classes with weights of 1e-3, 1e-9 and 1e9 are not mistaken for a separation** (the bound `wmin * 0.6931` of section 2.3; with `wmin` fixed at 1 that test fails); a view with a row stride bigger than the row; the same bits at 1, 2, 4 and 8 threads; 80 rounds of hostile weights (zeros, 1e-300, 1e12, 1.5e12, negative) that neither trap nor answer non-finite parameters.
* **WG5, scikit-learn** (`scripts/gate_weights_sklearn.py`, bounds fixed in the file: 1e-9 relative for `Ridge(sample_weight)`, 1e-6 for `LogisticRegression(sample_weight)` with `C = 1 / (l2 sum(w))`, scikit-learn 1.8.0): linear worst gap 2.4e-15, logistic worst gap 4.7e-8; the control (scikit-learn fitted without the weights) exceeds the bound on all 8 cases (0.0039 to 0.042).
* **WG9, mutants** (`scripts/mutants_models.py w- lin-count`): the 24 new mutants and 6 others of the same files: **30 killed, 0 survive**. The whole models gate (`scripts/gate_models.sh`) takes 37 s here.

The matrix is copied once for the linear fit (`n * d * 8` bytes, section 2.2); the logistic one copies the labels and the weights (`16 n` bytes), and a threaded pass copies the weights of each piece as it copies the labels.
